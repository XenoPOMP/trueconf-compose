# Миграция TrueConf Server с Windows на этот Docker-проект

Эта инструкция описывает перенос TrueConf Server, работающего на Windows, на
Linux-хост с этим Docker Compose проектом (`../docker-compose.yml` + `install.sh`).

Перенос состоит из трёх частей (по
[официальной инструкции TrueConf](https://trueconf.com/blog/knowledge-base/how-to-transfer-trueconf-server-data-between-windows-and-linux)):

1. **Дамп базы данных** (`pg_dumpall`) — отчёты и история чатов.
   `../install.sh` умеет автоматически применять его при первом запуске —
   см. блок "Checking for dump to import" в `install.sh`.
2. **Экспорт реестра сервера** (`tc_regkey`) — пользователи, группы,
   конференции, LDAP, настройки SIP/H.323, WebRTC, федерации. Это отдельный
   шаг: дамп БД его **не** заменяет (см. шаги 1.2 и 5.1).
3. **Файлы на диске** — чаты, аватары, записи, HTTPS-сертификаты.

> ⚠️ По официальной инструкции версия нового сервера должна **совпадать** с
> версией старого. TrueConf не публикует старые сборки, поэтому, если версия
> на Windows ниже тега образа (`TC_IMAGE_TAG` в `../.env`), сначала
> обновите Windows-сервер до той же версии. Если обновлять нельзя, образ сам
> накатывает "schema patches" поверх импортированного дампа при старте
> (см. лог `tcs_db_dump-*.log`), и для сборок одной ветки (например,
> `5.5.5.10010` → `5.5.5.10303`) это, как правило, работает, но официально
> не гарантируется. Откат версии после такого импорта невозможен — не
> выключайте и не трогайте старый сервер, пока новый не проверен.

## 0. Перед началом

- Не трогайте и не выключайте рабочий Windows-сервер, пока новый
  Docker-сервер не будет проверен и подтверждён рабочим. Он остаётся
  "путём отката" на всё время миграции.
- Уточните лицензию TrueConf. Регистрационный ключ привязан к
  **аппаратному ключу (HW key)** — контрольной сумме конфигурации машины
  (модель процессора, число vCPU/ядер, модель материнской платы,
  разметка диска с ОС, сама ОС). При переезде на другую машину/ОС он
  меняется, и дамп БД с записью о старой активации на новом сервере
  валидным не будет — сервер останется незарегистрированным
  (звонки и чат не работают). **Server ID** (первые 5 символов ключа,
  вкладка "Summary") при этом не меняется — его берут со **старого**
  сервера. Сброс привязки делает только поддержка TrueConf (бесплатно, по
  заявке с Server ID). Это долгая по времени часть, поэтому стоит делать её
  **параллельно** с остальными шагами:
  1. Не регистрируйте новый сервер после установки — сначала нужно
     восстановить данные и получить от поддержки сброс привязки.
  2. Зайдите в панель управления **старого** сервера, вкладка
     "Summary" → "License info", и запишите Server ID и имя сервера
     (имя нужно сохранить прежним, иначе сообщения в чатах перестанут
     отображаться — отправитель определяется по полному TrueConf ID).
  3. Обратитесь в поддержку TrueConf с этим Server ID и просьбой сбросить
     привязку к оборудованию (форма:
     <https://trueconf.com/support/technical-support.html>). Пока ждёте
     ответа — занимайтесь остальными шагами миграции (дамп, реестр,
     копирование файлов, установка с восстановлением).
  4. Найдите исходный регистрационный ключ (письмо с регистрацией; письмо
     можно найти по Server ID). Из панели управления ключ восстановить
     нельзя, а для повторной регистрации на новом сервере он нужен целиком.
  5. Не отключайте и не деактивируйте лицензию на Windows-сервере, пока
     от поддержки не придёт подтверждение, что регистрация на
     Docker-сервере прошла. Один ключ не должен одновременно работать на
     двух серверах (ошибка аппаратного ключа) — уточните у поддержки, можно
     ли держать старый сервер включённым до завершения переноса.
  6. Если у серверов нет доступа в интернет (`reg.trueconf.com:4310`),
     регистрация возможна только офлайн: в панели вводите ключ →
     "Регистрация" → "Создать файл регистрации" (`offlinereg.vrg`),
     отправляете файл в поддержку/`sales@trueconf.com` через любой компьютер
     с интернетом, получаете `offline2.vrg` и загружаете его в панель.
     Офлайн-регистрация недоступна для бесплатной лицензии. Пока ждёте
     ответа, процесс не перезапускайте.
  7. После успешной регистрации зафиксируйте конфигурацию машины
     (число vCPU, модель процессора, размер диска) и избегайте крупных
     обновлений ОС — они могут снова сломать привязку. Не используйте
     `docker-compose down`/`up` для перезапуска (контейнер пересоздаётся, а
     TrueConf предупреждает о риске аннулирования лицензии) — перезапускайте
     `docker restart trueconf-server`.
- Убедитесь, что новый хост умеет поднять Docker/Docker Compose и имеет
  доступ (по сети) к старому Windows-серверу, либо способ скопировать
  файл дампа (USB, SCP, общая папка и т.д.).

## 1. Снять данные на Windows-сервере

Откройте `cmd`/PowerShell **от администратора**. Пути ниже — стандартные
(`C:\Program Files\TrueConf Server`); если вы устанавливали сервер в другое
место, подставьте свой каталог (посмотреть можно в `services.msc` →
служба TrueConf Server → "Путь к исполняемому файлу"). Рекомендуется
складывать всё в отдельную папку, например `D:\backup`.

### 1.1. Дамп базы данных

TrueConf Server на Windows использует встроенный PostgreSQL. По
умолчанию он слушает порт **5444** (на старых установках мог быть 5432 —
проверьте командой ниже):

```powershell
findstr port "C:\Program Files\TrueConf Server\database\conf\postgresql.conf"
```

Снимите полный дамп кластера (именно `pg_dumpall`, а не `pg_dump` —
`../install.sh` ожидает на вход файл формата `pg_dumpall`). Ключ `-c`
добавляет команды очистки объектов перед созданием — так дамп применяется
поверх уже созданной сервером базы (так делает и официальная инструкция
TrueConf):

```powershell
cd /d D:\backup
"C:\Program Files\TrueConf Server\database\bin\pg_dumpall.exe" -p 5444 -U postgres -c -f tcs_db.dump
```

Проверьте, что файл `tcs_db.dump` не пустой и открывается как текстовый
SQL-дамп. При большой истории чатов экспорт идёт долго.

### 1.2. Реестр сервера (`tc_regkey`)

Пользователи, группы, адресные книги, конференции, настройки LDAP,
SIP/H.323, WebRTC и федерации хранятся в реестре сервера, а **не** в
дампе БД. Экспортируйте реестр отдельным файлом:

```powershell
cd /d D:\backup
"C:\Program Files\TrueConf Server\tc_regkey.exe" export "" registry.csv
```

Команда только читает данные и безопасна для работающего сервера.
Откройте `registry.csv` и убедитесь, что файл не пустой.

> ⚠️ Если на вашей версии `tc_regkey.exe` отсутствует или экспорт даёт
> пустой файл — не продолжайте миграцию вслепую: уточните у поддержки
> TrueConf, где хранятся настройки и пользователи в вашей сборке.

### 1.3. Файлы на диске

Дамп БД и реестр **не** содержат бинарных файлов. Их нужно скопировать
отдельно из **рабочей директории** сервера (по умолчанию `C:\TrueConf`; её
путь указан в панели управления: "Dashboard" → "Settings" → "Work path"):

| Что | Где на Windows | Куда на новом сервере |
|---|---|---|
| Аватары | `avatars` в рабочей директории | `data/avatars` |
| Файлы чатов | `files` (точный путь — поле "Path" в разделе "File Storage") | `data/files` |
| Записи конференций | `Recordings` (точный путь — поле "Path" в разделе "Recordings") | `data/recordings` |
| HTTPS-сертификаты (если настроены) | `<каталог установки>\httpconf\ssl` | см. шаг 6 |

Пути в поле "Path" в панели управления надёжнее догадок по именам папок —
администратор мог изменить расположение при установке. Полный список
путей можно также сверить в разделе "Backup and Restore" документации
TrueConf для вашей версии.

На Linux `data/` — это содержимое `/opt/trueconf/server/var/lib` внутри
контейнера (см. `../docker-compose.yml`), поэтому `data/database`,
`data/dump`, `data/files` и т.д. — подпапки одного и того же дерева.
Копируйте файловые каталоги **до** первого запуска `../install.sh`.

Особенности копирования на Linux:
- **Длина имён файлов.** В NTFS имя файла — до 255 символов UTF-16, в ext4 —
  до 255 **байт** UTF-8, поэтому файлы с длинными кириллическими именами
  (примерно от 127 символов) могут не сохраниться.
- **SCP и нелатинские имена.** При копировании через SCP такие имена иногда
  портятся или вызывают ошибку "unexpected file name" — после копирования
  сверьте файлы с оригиналом и переименуйте вручную.
- **Файлы `*.resume_data`** (если они есть в каталоге `files`, это сборки
  до 5.5): внутри них записан абсолютный путь Windows. Исправьте его в
  каталоге с файлами, иначе скачивание файлов из чатов не заработает:

  ```bash
  sed -i 's save_path[1-9]*:C:\\TrueConf\\files\\ save_path75:/opt/trueconf/server/var/lib/files/ ' *.resume_data
  ```

  (путь `C:\TrueConf\files\` замените на реальный путь к файлам чатов на
  Windows; формат команды взят из официальной инструкции TrueConf).

## 2. Скопировать данные на новый сервер

Перенесите `tcs_db.dump` на машину с этим проектом, в папку
`data/dump/` (если сети между машинами нет — через флешку):

```bash
mkdir -p data/dump
scp user@windows-host:/C:/backup/tcs_db.dump ./data/dump/tcs_db.dump
```

В `data/dump/` должен лежать **ровно один** файл (кроме `.gitkeep`) —
`../install.sh` явно проверяет это и откажется работать, если файлов
несколько. Поэтому **реестр кладите в другую папку**, например
`data/import/` (она тоже попадёт внутрь контейнера как
`/opt/trueconf/server/var/lib/import/`):

```bash
mkdir -p data/import
cp /путь/к/registry.csv data/import/registry.csv
```

Файловые каталоги (`avatars`, `files`, `recordings`) скопируйте в
`data/` по таблице из шага 1.3.

## 3. Подготовить `../.env` и образ сервера

1. Если ещё не собирали релиз — выполните `../.idea/sh/prepare.sh` (или
   `.idea/sh/release.sh`), чтобы выбрать тег образа `trueconf-server` и
   сохранить его в `images/trueconf.tar` + `TC_IMAGE_TAG` в `.env`.
   Версия образа должна совпадать с версией на Windows либо быть новее
   (старее брать нельзя; см. предупреждение в начале файла). На Docker Hub
   публикуются не все сборки — список тегов можно посмотреть командой
   `curl -s "https://hub.docker.com/v2/repositories/trueconf/trueconf-server/tags?page_size=100&name=5.5" | jq -r '.results[].name'`.
2. Проверьте `../.env`:
   - `TC_IMAGE_TAG` — тег образа.
   - `ADMIN_USER` / `ADMIN_PASSWORD` — эти значения применяются **только
     к действительно пустой базе**. Поскольку мы восстанавливаемся из
     дампа, реальные админ-аккаунты придут из дампа Windows-сервера —
     используйте логин/пароль администратора со старого сервера.

## 4. Убедиться, что это "чистая" установка

Проверка в `../install.sh` применяет дамп только если каталога
`data/database` ещё не существует (то есть это свежая установка). Если
вы уже запускали `install.sh` на этом хосте раньше и там есть данные —
очистите их:

```bash
.idea/sh/clear-data.sh
```

⚠️ Это необратимо удалит всё содержимое `../data` на новом сервере. Не
запускайте эту команду, если там уже есть данные, которые нужно
сохранить.

## 5. Запустить установку

```bash
./install.sh
```

Скрипт сам:
- загрузит образ из `../images/trueconf.tar`;
- поднимет `docker-compose up -d`;
- дождётся, пока TrueConf Server на первом старте применит дамп и
  накатит схемные патчи;
- выведет хвост лога импорта дампа и удалит временный файл дампа из
  `data/dump/` после успешного импорта.

Следите за процессом:

```bash
docker logs -f trueconf-server
```

### 5.1. Импорт реестра

Когда `install.sh` отработал и дамп БД применён, импортируйте реестр.
Сначала уберите из `registry.csv` строки, специфичные для Windows (пути к
каталогам, строка подключения к БД, токены и т.п.). Фильтр написан через
фиксированные строки (`grep -F`), чтобы не мучиться с экранированием
обратных слэшей:

```bash
cat > /tmp/registry-skip.txt <<'EOF'
install_version
Configuration,Working Directory
ConfDefault,Working Directory
Configuration,Executable Path
Configuration,Recordings Path
Configuration,Ffmpeg Path
Configuration,Push Script
Configuration,File Storage Path
Configuration,version
Configuration,DB Connection String
WebManager,server_dir
WebManager,db_port
WebManager,group_security
WebManager,group_admin
WebManager,client_path
Transceivers
WebManager\API\AccessTokens
WebManager\API\RefreshTokens\
EOF
grep -vFf /tmp/registry-skip.txt data/import/registry.csv > data/import/registry.linux.csv
```

Список взят из официальной инструкции TrueConf по переносу на Linux.
Проверьте результат: в `registry.linux.csv` не должно остаться путей
Windows (`C:\`, `.exe`) — при необходимости удалите такие строки вручную.
Если у нового сервера **другой IP-адрес**, замените старый адрес на новый
в файле (с экранированием точек в `sed`).

Импортируйте реестр внутри контейнера и перезапустите **контейнер**
(не `down`/`up` — см. раздел 0, шаг 7):

```bash
docker exec trueconf-server /opt/trueconf/server/bin/vcs/tc_regkey import "" /opt/trueconf/server/var/lib/import/registry.linux.csv
docker restart trueconf-server
```

> ⚠️ Эта процедура описана TrueConf для установки на Linux через пакеты;
> в Docker-образе она не проверялась. Бинарник `tc_regkey` в образе
> находится по пути `/opt/trueconf/server/bin/vcs/tc_regkey`. Если
> импорт выдаёт ошибку — сохраните вывод команды и обратитесь в
> поддержку TrueConf, не очищайте `data/`.

### 5.2. Сброс настроек LDAP (если LDAP использовался)

В Windows и Linux разные значения LDAP по умолчанию. В панели управления
откройте "LDAP/Active Directory" → "LDAP settings" → "Advanced", нажмите
"Default", затем "Apply", после чего заново внесите свои нестандартные
параметры. Иначе возможны проблемы с авторизацией пользователей.

## 6. Проверка после миграции

- Зайдите в веб-интерфейс администратора под учётными данными со
  старого Windows-сервера (не под `ADMIN_USER`/`ADMIN_PASSWORD` из
  `../.env` — см. пункт 3).
- Сверьте список пользователей, групп и адресную книгу с Windows-сервером.
  Если пользователей нет, значит реестр не импортирован — повторите шаг 5.1.
- Проверьте аватары, историю чатов, сообщения и скачивание файлов из чатов.
- Проверьте SMTP, настройки шлюзов, отчёты и расписание конференций.
- Проверьте историю конференций/звонков, если она важна.
- HTTPS: если на Windows был свой сертификат, перенесите ключ и
  сертификат на новый сервер (в Docker-образе для этого предусмотрена папка
  `/ssl` с файлами `tls.crt` и `tls.key`; её нужно примонтировать в
  `../docker-compose.yml`) и затем примените их в панели: "Web" → "HTTPS".
- Сделайте тестовый звонок/конференцию, чтобы убедиться, что сервис
  полностью работоспособен.
- Проверьте статус лицензии в админ-панели нового сервера — она должна
  быть активной, а не в триальном/ограниченном режиме (см. пункт про
  Server ID в разделе "0. Перед началом").
- Только после успешной проверки — выводите старый Windows-сервер из
  эксплуатации.

## Откат

Пока Windows-сервер не выключен и не удалён — откат тривиален: просто
продолжайте использовать его, а Docker-инсталляцию остановите
(`docker-compose down`) и при необходимости пересоберите с нуля после
исправления проблемы (`../.idea/sh/clear-data.sh` → `./install.sh` с новым
дампом).
