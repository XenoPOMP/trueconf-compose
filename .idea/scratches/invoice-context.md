# Контекст для обращения в поддержку TrueConf

Цель: составить обращение в техподдержку TrueConf, чтобы **перенести
лицензию с ноутбука (Windows) на выделенный сервер (Astra Linux + Docker)**
и получить файлы/коды для регистрации без доступа в интернет.

Легенда: **[ФАКТ]** — сообщено пользователем или подтверждено репозиторием/
документацией, **[ЗАПОЛНИТЬ]** — данных нет, **[ПРОВЕРИТЬ]** — гипотеза.

---

## 1. Суть ситуации (со слов пользователя)

- Есть рабочий TrueConf Server на **ноутбуке с Windows** («старый сервер»).
  На нём активирована лицензия **`Enterprise Slave`**.
- Ключ для этой лицензии получал **не пользователь** (его получил кто-то другой,
  через поддержку TrueConf). Полного ключа и письма с ним у пользователя нет.
- Поднят **выделенный сервер** («новый сервер»): Astra Linux **1.7.6.15**,
  Docker **v25**, docker-compose **v1.29.0**. Это будет постоянный сервер.
- Задача: перенести на новый сервер **все данные** — учётные записи, аватары
  и т. п. — и сделать его основным.
- **Доступа в интернет нет ни на одной из двух машин, и подключить его нельзя.**
- Сейчас сервис на новом сервере запущен, но: БД и файлы **не перенесены**
  (пустая установка), регистрация **не пройдена** (нет доступа к серверу
  регистрации).

## 2. Чего хотим от поддержки

1. Снять привязку лицензии `Enterprise Slave` к оборудованию ноутбука
   (hardware key) и разрешить регистрацию на новом сервере
   (без этого будет ошибка «Computer change is not available for this server
   code» / «CHECK CERT: HW key is failed!»).
2. Провести **офлайн-регистрацию**: мы присылаем `offlinereg.vrg`, получаем
   `offline2.vrg` (и ключ, если его нужно выдать заново).
3. Подтвердить, что при переносе сохранится **имя сервера** (ServerName) —
   иначе история чатов из дампа станет недоступна.
4. Уточнить порядок действий для схемы Master/Slave (см. п. 4): что делать
   с Master-сервером и License Manager после замены Slave-сервера.

## 3. Данные о серверах

### Старый сервер (ноутбук, Windows)
- [ФАКТ] ОС: Windows; продукт: TrueConf Server; лицензия: `Enterprise Slave`.
- [ЗАПОЛНИТЬ] Версия TrueConf Server (нужна для совместимости дампа БД с
  образом `5.5.5.10303`; если разрыв большой — спросить поддержку).

- [ЗАПОЛНИТЬ] **Имя сервера** (ServerName, `<id>.trueconf.name#vcs` или FQDN)
  — берётся там же, в Summary / настройках.
- [ЗАПОЛНИТЬ] Срок действия лицензии, число пользователей/подключений.
- [ЗАПОЛНИТЬ] Продолжает ли ноутбук работать и регистрироваться (и как, если
  интернета нет).

### Новый сервер (выделенный)
- [ФАКТ] Astra Linux 1.7.6.15, Docker 25, docker-compose 1.29.0,
  без интернета.
- [ФАКТ] Развёртывание: этот проект (`install.sh` + `docker-compose.yml`),

  контейнер `trueconf-server`, `network_mode: host`, `cap_add: SYS_ADMIN`,
  `seccomp:unconfined`, данные в `./data` → `/opt/trueconf/server/var/lib`.
- [ФАКТ] Состояние: контейнер запущен, **пустая БД, не зарегистрирован**.
- [ЗАПОЛНИТЬ] Какой IP/FQDN будет у сервера в сети, какое имя сервера
  (ServerName) нужно использовать (желательно то же, что на старом).
- [ПРОВЕРИТЬ] Обходные решения из `CLAUDE.md` (SYS_ADMIN, seccomp) подбирались
  на docker 20.10; на Docker 25 они, возможно, уже не нужны, но это
  не проверено и к лицензии не относится.

## 4. Что известно про `Enterprise Slave`

- [ФАКТ, по материалам TrueConf] Это не отдельный тип лицензии, а **роль
  сервера в связке Master → Slave** пакета TrueConf Enterprise. Лицензии
  покупаются на Master-сервер, а Slave-серверы берут их из общего пула
  через **TrueConf License Manager**. Точного описания SKU «Slave»
  в открытых источниках нет.
- Следствие: у Slave могут быть свой регистрационный ключ и привязка к
  железу, а объём лицензий определяется настройками на Master.
- [ЗАПОЛНИТЬ] Где находится **Master-сервер** (другая машина? у партнёра/
  заказчика?), кто им управляет, связан ли с ним ноутбук по локальной сети.
- [ЗАПОЛНИТЬ] Кто получил ключ для Slave (человек, организация, партнёр),
  есть ли у него исходное письмо с ключом и номер заказа.
- [ПРОВЕРИТЬ] Нужно ли после замены Slave перенастраивать License Manager
  на Master (новый Slave в пуле, удаление старого).

## 5. Регистрация без интернета

- [ФАКТ, из документации TrueConf] Онлайн-регистрация идёт через
  `reg.trueconf.com:4310`, поэтому в изолированной сети невозможна.
- [ФАКТ] Офлайн-регистрация недоступна для бесплатной лицензии, но
  доступна для платной/триала (`Enterprise Slave` — платный пакет, так что
  должна подходить; **[ПРОВЕРИТЬ]** у поддержки).
- Порядок (на новом сервере):
  1. В панели управления ввести регистрационный ключ → «Регистрация».
  2. «Создать файл регистрации» → получаем `offlinereg.vrg`.
  3. Перенести файл на машину с интернетом (флешка) и отправить
     на `sales@trueconf.com` (или в обращение в поддержку).
  4. Получить `offline2.vrg`, перенести обратно на сервер, в панели
     «Выбрать файл» → «Продолжить».
  5. Пока ждём ответ, процесс на сервере **не перезапускать** — иначе
     начинать заново.
- Интернет нужен только на «обычной» машине (рабочий компьютер), через
  которую идёт переписка с поддержкой. Серверы остаются изолированными.
- ⚠️ **Нужен полный регистрационный ключ**, чтобы запустить процедуру на новом
  сервере. Восстановить его из панели старого сервера нельзя (виден только
  Server ID). Значит, ключ надо найти у того, кто его получал, или
  попросить поддержку выслать его повторно.
- ⚠️ Один ключ не должен работать на двух серверах одновременно (hardware
  key error): в момент регистрации на новом сервере старый ноутбук
  лучше выключить/остановить — **но только после подтверждения от поддержки**
  (см. `guides/MIGRATIION_GUIDE_WINDOWS.md`, п. 0.5).

## 6. План переноса данных (чтобы не противоречить регистрации)

Основа — `guides/MIGRATIION_GUIDE_WINDOWS.md` (дамп `pg_dumpall` + каталоги
`var\lib` с аватарами, записями, вложениями).

1. Получить от поддержки сброс привязки и ключ/файлы (этот документ).
2. На ноутбуке: снять `pg_dumpall` и скопировать файловые каталоги из
   `var\lib` (аватары и т. д.). Версию TrueConf Server на Windows привести в
   соответствие с образом или уточнить совместимость.
3. На новом сервере: `.idea/sh/clear-data.sh` (БД пустая и не
   зарегистрирована, терять нечего), положить дамп в `data/dump/` и файлы в
   `data/<имя>`, запустить `./install.sh`.
4. Выполнить офлайн-регистрацию с тем же `ServerName`.
5. Проверить пользователей, аватары, звонки, статус лицензии; затем
   вывести ноутбук из эксплуатации.

## 7. Риски, о которых надо знать

- [ФАКТ, из документации TrueConf для Docker] `docker compose up/down`
  пересоздаёт контейнер и **может аннулировать лицензию**. TrueConf
  рекомендует `start`/`stop` вместо `up`/`down`.
- [ПРОВЕРИТЬ] Наш `install.sh` при каждом запуске делает `compose down`,
  `up -d` и удаляет старые образы `trueconf*`. После регистрации его
  повторный запуск (обновление) может сбросить регистрацию. Спросить
  поддержку, как правильно обновлять образ при выданной лицензии; возможно,
  придётся доработать `install.sh`.
- [ПРОВЕРИТЬ] От каких параметров считается hardware key в контейнере
  (`network_mode: host`, MAC-адрес, диски, hostname). Любое изменение
  железа/ВМ после регистрации снова сломает привязку.
- Не запускать `clear-data.sh` **после** регистрации — это удалит состояние
  сервера, включая регистрационные данные.
- Если имя сервера при перерегистрации изменится, предыдущие сообщения
  чатов станут недоступны (требование TrueConf, консультироваться с поддержкой).
- Известная мелочь проекта: `docker-compose.yml` читает логин админа из
  `ADMIN_LOGIN`, а в `.env` задан `ADMIN_USER` — логин всегда `admin`
  (после импорта дампа действуют учётки со старого сервера).

## 8. Что приложить к обращению

- Server ID (5 символов) и имя сервера со старого сервера.
- Версии: TrueConf Server на Windows, образ `5.5.5.10303` на Docker.
- Файл `offlinereg.vrg` (когда будет сформирован).
- Скриншот Summary → License info на старом сервере (со скрытым ключом)
  и текущего состояния нового сервера.
- Данные организации, номер заказа/договора, контакт того, кто получал ключ.

## 12. Ответы пользователя (интерактивный опрос)

- **Ключ:** полный регистрационный ключ у коллеги/партнёра (человек на связи,
  можно попросить письмо с ключом и номером заказа).
- **Master-сервер:** пользователь не знает, есть ли он. В обращении
  спросить поддержку, подчинён ли ноутбук Master-серверу и что нужно
  перенастроить в License Manager.
- **Имя сервера:** использовать то же, что на ноутбуке (ServerName берётся
  из Summary на ноутбуке).
- **Формат итогового документа:** письмо в поддержку на русском языке
  (форма https://trueconf.com/support/technical-support.html и/или
  `sales@trueconf.com`). Формальный счёт/заявка не нужны.
